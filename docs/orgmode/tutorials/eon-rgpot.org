#+TITLE: Minimise a structure from eOn through rgpot
#+OPTIONS: toc:nil todo:nil num:nil author:nil title:t

This tutorial relaxes the water molecule of the
[[file:first-energy.org][first tutorial]] with eOn's minimiser, with every force
call going through ~rgpot~ into ~libcpmdc~ inside the ~eonclient~ process.
It reuses ~water.params.bin~ from that tutorial and the OpenCPMD build of
~libcpmdc~ in ~$CPMDC/build-cpmd~.
Run every command in the Pixi shell that the first tutorial opened.

* What connects to what
eOn's ~RGPOT~ potential loads rgpot's ~CPMDPot~, which opens ~libcpmdc.so~
with ~dlopen~ and keeps one ~CPMDCSession~ for the life of the client.
eOn hands each geometry to ~CPMDPot~, ~CPMDPot~ turns it into a ~ForceInput~,
and ~cpmdc~ runs the SCF in the same process, starting every call after the
first from the previous orbitals.
The method comes from a ~CPMDParams~ message file that eOn reads through
~[RgpotPot] params_path~.

You need an ~eonclient~ built with RGPOT support whose ~[RgpotPot]~ section
reads ~params_path~; eOn lists the key under ~RgpotPot~ in ~eon/config.yaml~.
Without ~params_path~, eOn builds ~CPMDParams~ from four scalar keys
(~functional~, ~cutoff_ry~, ~charge~, ~multiplicity~).
A positive cell is then periodic: symmetry 1 when the edges are equal,
symmetry 8 when they are not, and ~CELL VECTORS~ with no symmetry line when
the box is tilted.
A zero cell stays ~SYMMETRY 0~ with the Hockney solver.
To keep a molecule isolated, the message has to ask for it.
This run uses ~water.params.bin~, which sets ~poissonSolver = "HOCKNEY"~, and
stays isolated.

* Build eonclient
This section builds rgpot and eOn into one prefix with the compilers and
libraries of cpmdc's Pixi environment.
eOn's own ~pixi.toml~ does not load under Pixi 0.84.2: its task ~mkeon~
depends on an environment ~eon~ that the file does not define.
cpmdc's environment has no Eigen, and eOn needs Eigen 3.4.
Install it as a separate Pixi environment:

#+begin_src bash
pixi global install 'eigen>=3.4,<3.5'
#+end_src

Work in the directory that holds the cpmdc checkout and ~cpmdc-tutorial~:

#+begin_src bash
cd "$CPMDC/.."
export EON_PREFIX=$PWD/eon-prefix
export PKG_CONFIG_PATH=$EON_PREFIX/lib/pkgconfig:$CONDA_PREFIX/lib/pkgconfig:$HOME/.pixi/envs/eigen/share/pkgconfig
#+end_src

~$CONDA_PREFIX/lib/pkgconfig~ is on the list because Meson can pick a system
~pkg-config~ that does not search the Pixi environment.
Build rgpot with MPI and install it:

#+begin_src bash
git clone https://github.com/OmniPotentRPC/rgpot.git
cd rgpot
git checkout 5fec533f
meson setup bbdir --prefix="$EON_PREFIX" --libdir=lib \
  -Dwith_rpc=true -Dwith_mpi=enabled -Dwith_fortran_pots=enabled \
  -Dwith_expr=true -Dwith_tests=false
meson install -C bbdir
cd ..
#+end_src

~with_rpc~ builds ~CPMDPot~.
~with_mpi~ builds ~librgpot_mpi~, which rgpot loads only when the client runs
under ~mpirun~.
eOn's configure stops when the installed rgpot has no Fortran potentials.
~with_expr~ matches the rgpot that eOn builds when it finds none installed.
Then build eOn against the installed rgpot:

#+begin_src bash
git clone https://github.com/TheochemUI/eOn.git eon
cd eon
git checkout 579738a93
meson setup bbdir --prefix="$EON_PREFIX" --libdir=lib -Dwith_mpi=enabled
meson install -C bbdir
cd ..
export PATH=$EON_PREFIX/bin:$PATH
#+end_src

Meson reports ~rgpot found: YES 3.7.0~ and uses the installed rgpot instead of
its own copy.
~-Dwith_mpi=enabled~ makes eOn build ~librgpot_pot_mpi~, which starts MPI for
the calculator groups and ends it at exit.
eOn builds that library when ~rgpot.pc~ defines ~RGPOT_HAS_MPI~ or when its
own ~with_mpi~ is on.
rgpot 5fec533f puts the define in ~rgpot-mpi.pc~ instead, so ~with_mpi~ is
the switch that works here.
The same ~eonclient~ runs on one rank without ~mpirun~.

Start in the directory that holds ~cpmdc-tutorial~, the one ~cd "$CPMDC/.."~
chose above:

#+begin_src bash

eOn lists each element in one component.
~cpmdc~ also accepts a step whose atoms of one element are split: it places
positions into CPMD's species blocks and returns forces in the order of the
input.

Save the eOn settings as ~config.ini~:

#+begin_src ini
[Main]
job = minimization

[Potential]
potential = rgpot

[RgpotPot]
backend = cpmdc
params_path = water.params.bin
#+end_src

~backend = cpmdc~ selects rgpot's ~CPMDPot~.
~params_path~ is read relative to the directory ~eonclient~ runs in.
~RGPOT_PARAMS_PATH~ in the environment overrides it.

* Run the minimisation
Point rgpot at the library and CPMD at the pseudopotentials, then start the
client:

#+begin_src bash
export CPMDC_LIBRARY=$CPMDC/build-cpmd/libcpmdc.so
export CPMDC_PSEUDO_DIR=$PWD/../cpmdc-tutorial/Regtests/tests/PP_LIBRARY
export OMP_NUM_THREADS=1
eonclient
#+end_src

rgpot tries ~[RgpotPot] engine_path~ first, then ~CPMDC_LIBRARY~,
~RGPOT_CPMDC_ENGINE~, and ~RGPOT_CPMD_ENGINE~, then ~libcpmdc.so~ on the
loader path.
CPMD writes its output for each force call to the client's standard output.
The first call starts from atomic orbitals; later calls start from the
previous call's orbitals and need fewer SCF iterations.

When the run ends, the directory holds:

| File | Contents |
|------+----------|
| ~min.con~ | the relaxed structure |
| ~results.dat~ | the termination status, the potential name, the number of force calls, the final energy in eV, and build provenance |

eOn works in eV and Angstrom; rgpot converts from the Hartree and
Hartree/Bohr values that ~cpmdc~ returns.

* Change the method
Edit ~water.params.txt~, encode it again, and rerun; eOn needs no other
change:

#+begin_src bash
capnp encode "$CPMDC/schema/Potentials.capnp" CPMDParams \
  < ../cpmdc-tutorial/water.params.txt > water.params.bin
#+end_src

To see what CPMD receives, set ~CPMDC_DECK_OUT=$PWD/deck.inp~ before
~eonclient~ (see [[file:../howto/debug-deck.org][debugging a deck]]).
For a periodic system or a larger cluster, write the message as the
[[file:../howto/write-cpmdparams.org][CPMDParams how-to]] shows, and choose the
optimiser for warm starts with the [[file:../howto/wavefunction-optimiser.org][optimiser
how-to]].

* Run on several ranks
Start ~eonclient~ under ~mpirun~ to let CPMD spread each SCF over the ranks:

#+begin_src bash
mpirun -np 4 eonclient
#+end_src

Every rank runs the whole client.
rgpot binds the four ranks into one calculator and hands its communicator to
~cpmdc_adopt_calculator_comm()~.
Only CPMD's parent rank holds the calculator's result.
eOn broadcasts that result to every rank, and rgpot finalizes MPI at exit.
[[file:../howto/mpi.org][Running under mpirun]] explains these rules.

With the build above and the same files, CPMD split each SCF over four
processors, and only the parent rank printed.
Each call took as many SCF iterations as on one rank.
~results.dat~ again reported ~GOOD~ and 7 force calls, with
~-4.641301944941e+02 potential_energy~, 1.2e-9 eV from the one-rank energy.
~mpirun~ returned 0.

Before cpmdc accepted an adopt while a session had not evaluated yet, every
rank stopped here, because rgpot creates its session before it binds the
ranks:

#+begin_src text
eonclient: fatal error: RGPOT(cpmdc): ranks_per_image=0 does not divide the MPI world into calculator groups
#+end_src

With rgpot and eOn built without MPI, the four ranks finished the
minimisation, but they exited without ~MPI_Finalize~ and ~mpirun~ returned 1.
